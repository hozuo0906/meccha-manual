# オンボーディング

Status: Accepted

## 目的

初回利用者が管理概念を学ぶ前に、実際の手順書を1本完成し、共有できる状態まで到達することをオンボーディングの目的とする。

オンボーディング完了は「ログインできた」「workspaceを作った」ではなく、`Chrome拡張導入 -> 操作を記録 -> 下書き生成 -> 編集 -> 共有` の完遂で判定する。

## 初回導線

1. LPまたは招待導線から開始する。
2. メールOTP等で認証する。
3. 個人利用者には内部workspaceを自動準備する。
4. 初回画面で `Chrome拡張を追加して最初の手順書を作る` を主要CTAとして表示する。
5. Chrome拡張を導入する。
6. 拡張の導入完了をアプリ側で確認し、`記録を始める` を主要CTAとして表示する。
7. 必要であれば短い用途選択を行う。
   - 経費精算
   - 勤怠・申請
   - CRM / 顧客管理
   - その他
8. 記録開始前に、対象タブだけを記録すること、入力値やCookie等を保存しないことを短く案内する。
9. 利用者が普段使っている業務画面で操作を記録する。
10. 記録終了後、自動生成された下書きを表示する。
11. タイトル、説明、不要ステップ、マスキングだけを優先して修正できるようにする。
12. `共有する` を主要CTAとして表示する。
13. 共有後に成功状態を表示し、次の行動として `2本目を作る` と `メンバーを招待` を案内する。

## 初回に要求しないこと

次は価値体験より前に利用者へ設定させない。

- workspace名の決定。
- owner/admin/editor/viewerの理解。
- メンバー管理。
- 保存容量の選択。
- revisionや公開版の内部構造理解。
- 料金プランの比較。
- Stripe決済。
- Browser Run時間や同時ブラウザ数の理解。

安全上必要な同意や権限説明は例外とするが、長い説明文を読まないと開始できない構造にはしない。

## Chrome拡張導入画面

初回価値までの最大の新しい摩擦点は拡張インストールであるため、1画面で目的を理解できるようにする。

表示する内容:

- `Chromeに追加して操作を記録する` の主要CTA。
- 「普段の業務画面をそのまま操作すると、手順書になります」の一文。
- 「記録開始したタブだけを対象にします」。
- 「入力した文字列、パスワード、Cookieは保存しません」。
- インストール後に自動または1クリックでアプリへ戻る導線。

`activeTab`、`scripting`、Manifest V3等の技術用語は通常利用者へ説明しない。Chromeが表示する権限警告と実際の拡張権限が一致することを事前に検証する。

## 初回画面

### 空状態

初回ログイン後に空の表だけを見せない。

表示優先度:

1. Chrome拡張が未導入なら `Chrome拡張を追加する`。
2. 導入済みなら `最初の手順書を作る`。
3. 「操作を一度記録すると、画像付きの手順書になります」の一文。
4. 安全性についての短い補足。
5. 必要な場合のみサンプルを見る導線。

### 記録開始前

最低限伝えること:

- 今から開いている対象タブだけを記録する。
- 入力した文字列そのものは保存しない。
- パスワード、カード番号、Cookie、Authorization等は保存しない。
- 記録停止後はそのタブの継続監視を行わない。

利用者にcontent script、Chrome API、R2、D1等の技術用語を表示しない。

### 記録中

記録中であることを拡張アイコン、badge、side panel等の一貫したUIで明示する。

最低限必要な操作:

- 記録停止。
- 一時停止が必要かはMVP実装時に最小価値で判断する。
- エラー時に現在まで保存済みかを確認できる。

記録対象外の別タブへ移動した場合、勝手に記録対象を広げない。

### 記録失敗

エラーは次の順で表示する。

1. 何が起きたか。
2. どこまで保存されたか。
3. 次に何を試せるか。

特定サイトのDOM構造等で継続できない場合は、無限再試行させず、手動で手順を作る・対象ページを再読み込みして試す等の安全な代替導線を提示する。

### 下書き生成後

最初から全編集機能を展開しない。

優先操作:

- タイトルを直す。
- 不要なステップを消す。
- 説明文を直す。
- 必要箇所をマスキングする。
- 並べ替える。

高度な設定は折りたたむか、通常導線外へ置く。

### 完成・共有

共有完了時は成功を明確に伝える。

主要行動:

1. 共有リンクをコピー。
2. 2本目の手順書を作る。
3. 必要な場合だけメンバー招待。

課金案内は、無料枠の価値を体験する前に主要CTAとして出さない。

## Activation定義

Activationは次の条件をすべて満たした時点とする。

- Chrome拡張が利用可能な状態になっている。
- 初回manualが作成されている。
- 1件以上のstepが存在する。
- 利用者が生成結果を確認している。
- manualが共有可能な状態になっている。

共有URLを実際に他者が閲覧した場合は `Activated + Shared` として別に計測する。

## 計測イベント

最低限次を記録する。

| event | 意味 |
|---|---|
| `onboarding_started` | 初回導線開始 |
| `extension_install_started` | Chrome拡張導入開始 |
| `extension_install_completed` | Chrome拡張利用可能 |
| `capture_started` | 記録開始 |
| `capture_failed` | 記録失敗 |
| `capture_completed` | 記録終了 |
| `draft_generated` | 下書き生成 |
| `first_manual_completed` | 最初の手順書完成 |
| `share_enabled` | 共有有効化 |
| `shared_manual_viewed` | 共有先で閲覧 |
| `second_manual_created` | 2本目作成 |
| `member_invite_started` | チーム拡張意図 |
| `upgrade_started` | 課金意図 |
| `upgrade_completed` | 課金完了 |

イベントpayloadへ入力値、Cookie、Authorization、スクリーンショット本文、機密queryを含めない。

## UX KPI

- Extension Install Completion Rate。
- Activation Rate。
- TTFV。
- Capture Completion Rate。
- Share Rate。
- Second Manual Rate。
- D7 Creator Retention。

初期改善では、設定画面の機能充実よりこれらの指標改善を優先する。

## Teamへの拡張

個人が価値を得た後にだけTeam機能を段階的に開示する。

`共有 -> 繰り返し利用 -> メンバーを招待したい -> Team機能を案内`

メンバー招待開始までは、4ロールや席数を初回体験の中心に置かない。

## セキュリティ境界

オンボーディング簡素化を理由に次を弱めない。

- Access主体検証。
- workspace/tenant分離。
- private storage。
- Chrome拡張の最小権限。
- 利用者の明示操作なしに記録開始しないこと。
- 対象タブ以外を継続監視しないこと。
- 入力値、Cookie、Authorizationの非保存。
- 共有リンク失効。
- ログへのsecret非出力。

Browser Runを将来再導入する場合は、その時点でSSRF/egress fail closedを再度必須境界にする。
