# UX原則

Status: Accepted

## 基本方針

`めっちゃマニュアル` はWikiではありません。操作を記録し、業務手順として確認、公開、更新するための作業台です。

最初のUX目標は、利用者に管理機能を理解させることではなく、最短で `操作を記録 -> 下書きを確認 -> 必要最小限編集 -> 共有` を完了してもらうことです。

## Time to First Value

- 初回利用では、価値体験に不要な設定を先に要求しない。
- workspace、role、storage、usage、revisionなど内部概念を、必要になるまで利用者へ見せない。
- 初回ログイン後の主要CTAは原則1つに絞り、`最初の手順書を作る` または `操作を記録する` へ導く。
- 空の一覧だけを表示して利用者へ判断を委ねず、次の行動と所要ステップを示す。
- 初回手順書の完成・共有までをオンボーディングの完了とする。

## Progressive Disclosure

- 個人利用者には、自分専用の内部workspaceを自動準備してよいが、workspace作成を初回タスクにしない。
- `メンバーを招待` を選ぶまでロール管理を前面に出さない。
- 課金上限や保存容量は通常状態で常時表示せず、意思決定に必要なタイミングでだけ案内する。
- 下書き／公開版など内部状態は必要最小限の利用者語彙に変換し、通常画面では `編集中` / `公開中` を基本とする。
- 高度な設定は基本導線の外に置く。

## 画面原則

- 一覧は表を基本にする。ただし初回空状態は作成導線を最優先する。
- 手順書閲覧は縦スクロールを基本にする。
- エディタは通常時に手順一覧と内容を中心とし、編集が必要なときだけ詳細パネルを開く段階的UIを優先する。
- 常時3ペイン固定を必須にせず、狭い画面や初心者利用では情報密度を下げる。
- 設定はフォームで扱う。
- 何でもカードにしない。
- 公開閲覧画面に管理画面用ナビゲーションを出さない。
- 主要CTAを同じ視覚階層で複数並べない。

## 初回オンボーディング原則

- 製品説明より先に成功体験を作る。
- チュートリアルだけで完了扱いにせず、実際の手順書1本を完成させる。
- サンプルデータは選択肢として提供してよいが、利用者自身の業務で作る導線を主とする。
- 初回記録開始前に、入力値を保存しないことと記録できない可能性があるサイトを短く案内する。
- 記録失敗時は技術用語ではなく、代替手段または次の行動を提示する。
- 完成時は `共有する` を次の主要行動とし、その後に2本目作成やチーム招待を提案する。

## 文言

- 丁寧だが短い `です・ます` 調。
- 英語やカタカナの多用を避ける。
- ボタンは行動を明示する。例: `作成` ではなく `手順書を作成`。
- エラーは `何が起きたか -> どこまで保存されたか -> 次に何をするか` の順に書く。
- `workspace`、`revision`、`entitlement` 等の内部語彙を一般利用者向け画面へ直接出さない。

## 状態

各画面で以下の状態を設計する。

- 空
- 読込中
- 保存中
- 保存済み
- 保存失敗
- 権限不足
- 接続切断
- 期限切れ
- 容量超過

状態を増やす場合も、利用者が次に取る行動が変わらない内部状態は統合して表示する。

## Product UX計測

最低限、次を観測できるようにする。

- 初回ログインから記録開始までの離脱。
- 記録開始から下書き生成までの離脱。
- 下書き生成から完成までの離脱。
- 完成から共有までの離脱。
- 初回完成までの所要時間。
- 7日以内の2本目作成。

計測のために入力値や秘密情報を保存しない。

## アクセシビリティ

- 色だけで状態を伝えない。
- ドラッグ操作にはボタン操作の代替を用意する。
- アイコンボタンにはツールチップとアクセシブル名を付ける。
- 本文16px以上、一覧14px以上、タッチ対象44px以上を目安にする。
- 初回導線でもキーボード操作とフォーカス移動を省略しない。
