# リファクタリング・コードレビュー方針

Status: Accepted

## 責務

リファクタリング担当はコードをきれいにする係ではなく、仕様、責務、依存関係が壊れる前に止める門番です。

## チェックリスト

- PRの目的が一文で説明できる。
- 無関係な変更が混ざっていない。
- 新しい責務の所有モジュールと依存方向が明確。
- 同義の定数、型、状態、変換処理が既に存在しない。
- 名前が責務、単位、同期/非同期、失敗可能性を表している。
- 環境変数の直接参照、秘密情報のログ出力、危険なデフォルトがない。
- 認証済みと認可済みを混同していない。
- 状態遷移に不正経路、競合、二重実行、途中失敗が考慮されている。
- Stripe webhook、Browser job、Durable Object commandが冪等。
- 外部SDK型がドメイン型へ侵入していない。
- テストが契約と失敗経路を検証している。
- MD、状態遷移表、API契約、DB migration、実装が一致している。

## PRごとの許容範囲

- 小規模機能PR: 変更対象周辺の命名、重複除去まで。
- バグ修正PR: 再現テストと最小修正が原則。
- 横断機能PR: 先にADRと移行計画を承認。
- 専用リファクタリングPR: 挙動不変をテストで証明。
- DB/RLS PR: migration、rollback、既存データ影響、RLS検証を一組にする。

`ついでに` が出たらPR分割対象です。
